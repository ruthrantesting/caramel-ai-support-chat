# Data Model: User Authentication for the Caramel AI Tech Support Chat

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Research**: [research.md](research.md)

Accounts are the only durable data in the MVP (Constitution VI). Everything else (sessions, conversation ownership, chat memory, throttle and rate-limit state) stays in process memory and is lost on restart. This does not change the 001 rule that chat history is not persisted.

## Durable data (database)

### User (`users` table)

| Field | Type | Rules |
|-------|------|-------|
| `id` | UUID | Primary key. Generated by the server at sign-up (random, not sequential). This is the "authenticated user ID" given to the chat service. |
| `email` | text, max 254 | Unique. Stored trimmed and lowercased. Must be a well-formed address (FR-002). Two addresses that differ only in case are the same account. |
| `password_hash` | text | Output of the delegating password encoder (Argon2id by default, with an algorithm prefix). Never returned, never logged (FR-005). |
| `created_at` | timestamp with time zone | Set at sign-up. |

**Validation at sign-up** (FR-001 to FR-004):

- Email: not blank, at most 254 characters, well formed after trimming, lowercased before the uniqueness check.
- Password: Unicode-normalized (NFKC), 12 to 128 code points, not on the common-password list (compared case-insensitively). No composition rules.
- A duplicate email is refused with a neutral message (FR-006). The unique index is the final guard against two simultaneous sign-ups. The violation is mapped to the same neutral response.

No roles, profile, or deletion fields exist (out of scope).

### Password reset token (`password_reset_tokens` table, User Story 6 only)

| Field | Type | Rules |
|-------|------|-------|
| `token_hash` | text (SHA-256 hex) | Primary key. Only the hash is stored. The token itself is only in the email. |
| `user_id` | UUID | Foreign key to `users.id`. |
| `expires_at` | timestamp with time zone | Issue time plus 60 minutes (FR-026). |
| `used_at` | timestamp with time zone, nullable | Set when the token is used. A token with `used_at` set is refused. |

**States**:

```text
issued --use before expires_at--> used        (password changed, other sessions ended)
issued --time passes expires_at--> expired    (refused)
used / expired --any use--> refused
```

A new request for the same user does not need to invalidate older tokens, but all of a user's outstanding tokens are marked used when a reset succeeds. Expired and used rows are deleted by a daily cleanup so the table cannot grow without bound.

## In-memory state (process-local, lost on restart)

### Session (container-managed)

| Field | Where | Rules |
|-------|-------|-------|
| session ID | `HttpOnly` cookie | Never readable by page scripts, never logged (FR-013, FR-024). Changed at sign-in to prevent fixation. |
| security context | session attribute | Holds the `AuthenticatedUser` (user ID and email). |
| `signedInAt` | session attribute | Set from the injected clock at sign-in. Used for the 7-day absolute limit (FR-011). |
| last access | container | Used for the 8-hour idle limit (FR-011). |

**Lifecycle**:

```text
(none) --register or login--> active
active --request within 8 h idle--> active
active --8 h without a request--> expired
active --7 days after signedInAt--> expired
active --logout--> ended
active --password reset of this user (User Story 6)--> ended
any    --server restart--> (none)
```

An expired or ended session makes the next protected request return `401` with code `UNAUTHENTICATED`.

### Authenticated user (principal)

A small immutable value holding `id` (UUID) and `email`. The controller passes only `id` to the chat service (Constitution V).

### Conversation ownership binding (inside `ConversationRegistry`)

Extends the 001 conversation entry (`specs/001-tech-support-chat/data-model.md`).

| Field | Type | Rules |
|-------|------|-------|
| `conversationId` | string (UUID) | Client-supplied. Canonical UUID format, as in 001. Registry key. |
| `ownerUserId` | UUID | Set once, atomically, by the first accepted `POST`. Never changes while the entry exists. |
| `lastActivityAt`, `inFlight`, `turn` | as in 001 | Unchanged. |

**Rules**:

- `POST` by the owner: accepted (or `409` if a turn is already in flight, as in 001).
- `POST` by another user, bound identifier: `404`, code `CONVERSATION_NOT_FOUND`. No state changes.
- `DELETE` by the owner: clears memory and the binding, `204`.
- `DELETE` by another user, or for an unknown identifier: `404`, no state changes.
- The binding is removed by an owner `DELETE`, by the idle expiry (2 hours, as in 001), and by a restart. Sign-out does not remove it.

**Chat memory key**: `<userId>:<conversationId>`. The conversation memory itself is still Spring AI chat memory in process memory, as in 001.

### Login throttle entry (per normalized email, registered or not)

| Field | Rules |
|-------|-------|
| `failures` | Count of consecutive failed sign-ins. Restarts after a quiet period longer than 15 minutes (research A-12). |
| `blockedUntil` | Set when `failures` reaches 5, to now plus a delay of 30 seconds doubling with each further failure, capped at 15 minutes. |

A successful sign-in clears the entry. Attempts while `blockedUntil` is in the future are refused with `429` and `Retry-After`, without checking the password. Entries with no failure in 15 minutes are purged.

### Rate-limit window (per key)

Sliding window of request times, as in 001.

| Limiter | Key | Default |
|---------|-----|---------|
| Chat messages | authenticated user ID | 20 per minute (FR-021) |
| Sign-in | client address | 10 per minute |
| Sign-up | client address | 5 per hour |
| Reset request | client address | 5 per hour |

The client address follows the 001 rule: the remote address, or the first `X-Forwarded-For` value only when `support.rate-limit.trust-forwarded-for` is on.

## Frontend state

| State | Values | Notes |
|-------|--------|-------|
| `auth.status` | `loading`, `signedOut`, `signedIn` | `loading` until the first `GET /api/auth/me` answers. The app shows nothing but a busy indicator during `loading`, so the sign-in form does not flash for a signed-in user. |
| `auth.user` | `{ id, email }` or none | Set from `me`, `login`, or `register`. |
| `auth.expiredFor` | user ID or none | Set when a `401` arrives while the chat is open. Opens the sign-in dialog and remembers which user the chat belongs to. |

**Transitions**:

```text
loading --me 200--> signedIn
loading --me 401--> signedOut
signedOut --login or register ok--> signedIn
signedIn --logout--> signedOut           (chat state cleared)
signedIn --401 on any call--> signedIn + expiredFor set (dialog open, chat kept)
expiredFor set --login as the same user--> expiredFor cleared (chat kept, user retries)
expiredFor set --login as another user--> expiredFor cleared, chat cleared, unsent text restored to the message box
```

The CSRF token and the session ID are never stored in the frontend state or in browser storage. The CSRF value is read from its cookie at request time.
